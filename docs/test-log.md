## 2026-09-24 · 第四轮：补四条库外走廊 + 青甘大环线 AI 生成实测

### 目标
把西藏 / 川西 / 青甘 / 内蒙四条走廊从 0 覆盖补到可用，并用一条新走廊的真实行程验收。

### 结果

| 项 | 补之前 | 补之后 |
|---|---|---|
| 点位库 | 58（只有新疆三条走廊） | **353**（西藏 76、川西 79、青甘 51、内蒙 64、新疆 83） |
| 约束库 | 52 | **141**（西藏 22、川西 22、青甘 22、内蒙 23、新疆 52） |
| allowlist | 2 项 | 77 项（省/全境/公路/区域级地点，显式声明） |
| 约束类型 | 10 类 | 10 类（reservation 19、season 29、vehicle 20、price 16、closure 16…） |

### 验收：Qwen 生成的青甘大环线 8 日（2026-07-15 → 07-22）

- **输入层**：markdown 表格，日期格写成 `**D1**<br>7.15` → 正确解析成 8 天、2026-07-15…22 ✓
- **点位识别**：**27 个点位全部命中新库**（西宁/青海湖/茶卡/大柴旦/水上雅丹/敦煌/莫高窟/张掖/七彩丹霞/祁连/门源…）✓
- **真实路网**：25 段、**3 690.6 km** ✓
- **约束挂载**：29 条，其中硬约束 29 条 —— 莫高窟 A 类每日 6000 张/238 元、青海湖二郎剑 1.2 万人实名预约、
  水上雅丹禁自驾换乘、七彩丹霞禁私家车、门源油菜花 7/10—8/5 ✓
- **时令判定**：青海湖 7/15 = 最佳「旺季全域开放」、门源 7/21 = 最佳「油菜花盛花 7/20 前后」✓

**Qwen 这份计划本身质量很高**（甚至提了「莫高窟 A 票提前 30 天」「U 型公路严禁停车」），
所以这次验收的重点不是"找出它的错"，而是**验证新走廊的数据链路能不能跑通**——结论是能。

### 这轮踩的坑（都修了，代码里留了注释）

**A. 输入层真 bug：文末第二张表被当成额外的天。**
Qwen 的行程在 8 天表后面还有一张"核心注意事项"表，结果被解析成 D9—D14，日期是"类别""票务与预约"。
修法：行程表每行都该有可解析日期，**连续两行解析不出就认为表格结束**；解析不出日期的行直接跳过。

**B. Overpass 查询，试错记录**（都在 `fetch_corridors.py` 的注释里）：
1. 一批 24 个名字 → "拉萨"这种通用名把 `out` 配额吃满，纳木错/羊卓雍措/江孜直接查不到
2. 有界正则 `^(?:A|B)(.{0,4})?$` → **400 Bad Request**
3. 精确正则 `^A|B$` → **504 Gateway Timeout**
4. 4 个进程并行 → **IP 级 429**（Overpass 按 IP 限流，只能单进程）→ 主站被限流后连不上，换法语镜像解决
5. 自估的子区块 bbox 太紧 → 江孜/羊卓雍措落在边界外，白跑一轮
6. `name~"正则"` 无法用索引，大 bbox 下每次 7—10 s；`name="精确"` 虽快但漏双语名
   （OSM 里布达拉宫写作「布达拉宫 ཕོ་བྲང་པོ་ཏ་ལ།」）
7. **分片只在跑完时写文件**，中途 kill 会丢结果 → 写了 `parse_logs.py` 直接从日志解析中间结果

**C. 命名不一致（藏区尤其严重）**：查询用的「纳木错」在 OSM 里叫「纳木湖」，
「羊卓雍措」根本查不到。已加 措/错/湖、朗/郎 变体派生，但仍会有查不到的，属正常。

**D. 匹配质量**：「大昭寺」被匹配到「田村·酸汤牦牛肉（大昭寺店）」、「纳木错」匹配到「纳木错里」。
修法：NOISE 扩充店铺/服务类词；"精确"改为**按 token 判定**（双语句名算精确）；
括号里带店名的候选降权。

**E. schema 语义冲突**：调研代理把 `place` 写成了"适用范围描述"
（如「冷湖—大柴旦—敦煌（G315 / G215 一带）」），而 `place` 是**挂载键**。
新增 `scope_text` 存原描述，`place` 只留可匹配的点位键；抽不出的要么补地名库、
要么显式进 `place_allowlist`。

**F. 覆盖度测试暴露的分类器缺陷**：我先用坐标给所有点位打走廊标签，
结果把 86 个新疆点位全归成了"其他"。改为：**新疆作为一个整体看总量，四条新走廊各自设门槛**。

### 仍缺什么（如实说）

1. **坐标置信度**：353 个点位里有 **125 个是 medium/low**（OSM 候选不唯一或名字不精确）。
   它们能用，但**交付前要在图上核验**——脚本已给每条打了 `note` 提示。
2. **覆盖是"种子"不是"全量"**：每条走廊约 50—80 个点位，覆盖经典路线的主要锚点，
   但一个具体行程冒出来的小众点位仍会"未解析"，需要现补（`add_places.py` 已把这一步工具化）。
3. **约束时效**：89 条新约束里，调研代理自己标注了 5—8 条"证据偏弱"（票价档位、
   限流数字的多口径冲突），都写进了 text 的"以官方公告为准"。这类数字建议每季度复核一次。
4. **冲突检测仍是人工**：skill 把约束和行程都摆出来，但"计划写顺时针 vs 官方东门进南门出"
   这种矛盾要人来发现（目前只有季节窗口做了结构化比对）。

### 外部 AI 实测：qwen3.6-plus 出一份伊犁 6 月行程

- **它给的格式**：markdown 表格，日期列写成 `**D1｜6.13**`
- **输入层**：一次通过（`D1｜6.13` 正确解析成 `2026-06-13`，10 个点位全命中）
- **体检发现 4 个问题**：
  1. D4「夏塔**轻徒步 3—5km**」撞上 **2026 年昭苏全域山区禁徒步露营**（硬冲突）
  2. D2「**顺时针**环湖」与官方单向（东门进南门出）相反
  3. 开头自称"单日行车 ≤3.5h"，实测 **D4 = 267 km / 6.6 h**（真实路网打脸）→ 重排节奏
  4. 薰衣草排在最后一天，其实就在去赛湖的路上 → 挪到 D2，并给库补了这条时令数据

**Qwen 的季节判断是对的**（6 月选伊犁、选夏塔/喀拉峻都没错），错的全是执行细节——
这印证了产品的定位：体检的价值不在选点，而在细节校验。

### 时令匹配器第一次运行就纠正了我自己做的案例

4 月伊犁案例把吐尔根杏花沟排在 4/22，而盛花窗口是 4/5—4/20（**过了峰值两天**）。
人工检查时没发现 → 案例日期前移 3 天。同时它正确报出"恰西/库尔德宁 4/18 不在任何窗口内"——
不是 bug，是事实（野花季 5 月中才起）。

### 本轮抓到的 skill 自身问题（并已修）

| 问题 | 现象 | 修法 |
|---|---|---|
| a | 决策说明类记录被当硬约束挂载（那条"4 月 vs 5 月"挂了 6 天） | 引入 `scope: "meta"`，两个脚本都跳过 |
| b | 时令约束不过滤日期（6 月行程挂着"4 月融冰季"） | 用 `window` 过滤：窗口不覆盖当天就跳过 |
| c | `match_season` 三个 bug：meta 污染、无时令数据的点被误报、跨年窗口边界 | 全修 + 写成 4 项测试 |
| d | 缺 `{{nights}}` 占位符 | 已加 |

a、b 是同一类问题的两面：库里混着"按地点挂载的约束"与"走廊级说明"、
"全年有效"与"仅某季节有效"的记录——原来没区分。现在拆成两个正交维度：
**`scope`（挂不挂）与 `window`（什么时候才有意义）**。
